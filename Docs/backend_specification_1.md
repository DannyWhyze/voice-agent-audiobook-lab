# Backend Specification 1: Architecture & Internals (FishAudio S2 Pro Lab)

This document is a technical reference for the FastAPI backend's internal architecture — module layout, data persistence, the TTS engine integration, the LangChain chat agents, and the audio DSP pipeline. It complements `docs/frontend-specification.md`, which covers the REST interface (routes, request/response shapes) needed to build or replace the frontend; this document covers what's *behind* that interface.

**Numbering:** this file is part of a numbered series (`backend_specification_1.md`, `_2.md`, ...), mirroring the `docs/JOURNAL_N.md` convention — when this file grows too large, a new one starts with a "Fortsetzung von `backend_specification_N.md`" pointer, rather than editing one ever-growing file (unlike `frontend-specification.md`, which stays a single file).

---

## 1. Module Layout

`src/orchestrator/` is a FastAPI application, structured by responsibility:

- **`main.py`** — app setup (CORS, static file mounting, router registration), plus the `/`, `/app`, and `/combine` routes that didn't fit any router's theme.
- **`routers/`** — one file per route group, all included into `main.py`'s `app`:
  - `voices.py` — voice listing/preview, creation (`POST /voices`), locking (`PUT /voices/{name}/lock`), renaming (`PUT /voices/{name}/rename`), deletion (`DELETE /voices/{name}`), detail listing (`GET /voices/detail`), and usage lookup (`GET /voices/{name}/usage`).
  - `projects.py` — dialog project/chapter CRUD (save, load, delete, rename, reorder chapters).
  - `variants.py` — per-box and combined-audio variant management (generate, compare, activate, delete, lock).
  - `effects.py` — the DSP effect endpoints (compressor, reverb, EQ, normalize, pitch, formant, trim, fade), table-driven registration (`EffectSpec`, see Plan 085).
  - `chat.py` — the two chat endpoints (box chat, script chat), see Section 4.
  - `presets.py` — effect-parameter presets (save/load/list named parameter sets per effect type).
  - `skills_files.py` — agent memory & skill files CRUD endpoints (`/skills-files`), path-traversal-safe, view/edit/delete existing files only.
- **`dialog/`** — persistence/business logic for dialog projects, separate from the HTTP layer in `routers/projects.py`:
  - `projects.py` — chapter JSON read/write, project directory management (see Section 2).
  - `variants.py` — variant storage logic backing `routers/variants.py`.
  - `effect_params.py` — per-box/combined effect parameter storage backing `routers/effects.py` and `routers/presets.py`.
  - `skills_files.py` — persistence layer for agent memory (`AGENTS.md`) and skill files (`<skill>/SKILL.md`), enforcing view/edit/delete only (no creation).
- **`audio/`** — pure DSP building blocks, no FastAPI/HTTP awareness, see Section 5.
- **`agents/`** — the two LangChain chat agents, see Section 4.
- **`engine_client.py`** — HTTP client for the `s2.cpp` TTS engine server (default `http://127.0.0.1:3030`, overridable via `ENGINE_URL` env var) plus voice-file access (`data/audio_data/voices/*.wav`+`.txt`).
- **`paths.py`** (2026-08-11) — resolves `STATIC_DIR`/`DATA_DIR`/`VOICES_DIR`/`DIALOG_PROJECTS_DIR`/`SKILLS_DIR` for both normal (`uv run`) and PyInstaller-frozen execution, see Section 6.
- **`schemas.py`** — shared Pydantic request/response models (e.g. `ChatRequest`).
- **`tags.py`** — the fixed `[tag]` vocabulary (emotion/emphasis tags) shared by both chat agents' system prompts and the frontend's tag panel (`GET /tags`).

## 2. Data Persistence

No database — flat JSON files on disk, rooted at `data/dialog_projects/` (`dialog/projects.py:DIALOG_PROJECTS_DIR`):

```
data/dialog_projects/<project>/
  <chapter>.json          # one file per chapter: boxes, speakers, effect params, variant refs
  _chapter_order.json     # explicit chapter ordering (drag-and-drop reorder, Plan 022)
  <chapter>_audio/        # persisted per-box + combined generated audio (Plan 017/023)
```

Project/chapter names are sanitized (`dialog/projects.py:sanitize_name()`, strips everything but `\w\- .`) and path-resolved against `DIALOG_PROJECTS_DIR` with an `is_relative_to()` check before any file access — the path-traversal fix from Plan 001/075/076.

`<chapter>.json`'s `boxes` list only grows on an explicit `PUT /projects/{project}/chapters/{chapter}` (chapter save) — boxes added client-side afterward don't exist there yet. `add_box_variant()` (`dialog/variants.py`, fixed 2026-08-07) self-heals this on demand: if `box_index` is beyond the current list, it appends empty placeholder box dicts up to that index (capped at `MAX_BOX_INDEX = 500`) before writing, so generation/effect-apply work without requiring a save first — the next real save overwrites the placeholders with actual box data. Negative indices are still rejected outright (path/index-bound hardening from Plan 077).

`box_{index}.wav` is purely positional — it says nothing about *which* logical box produced it, only which array slot it currently occupies. `save_chapter()` (`dialog/projects.py`, fixed 2026-08-08) actively guards this: besides deleting `box_N.wav` for indices beyond the new box count (a box removed from the end), it also deletes a *mid-array* index's `box_N.wav` whenever that save's incoming box list has empty `variants` for position N and no fresh clip is being written there — i.e. the client believes that slot is blank. Without this, a box inserted before/between existing ones (shifting every later box's index by one) or a box removed and replaced by a new one at the same position would leave a stale file behind that `add_box_variant()`'s "seed an Original variant from `box_N.wav`" check (only tests file existence) would silently re-adopt as if it belonged to the new occupant. The client-side write paths that must sync a chapter save immediately after any box-order change (not just append-at-end or explicit "Kapitel speichern") are `dialog-boxes.js`'s remove-box and insert-between handlers, and `dialog.js`'s insert-at-top handler — each calls `saveCurrentChapter({ silent: true })` (exported from `dialog-projects.js` for this purpose) right after mutating the DOM.

**Project rename (2026-08-08):** `rename_project(project, new_name)` (`dialog/projects.py`) renames a project's whole directory. Uses the same Windows-safe case-only-rename workaround as the pre-existing `rename_chapter()` — a case-insensitive filesystem can treat a source and target path as identical and silently no-op a direct rename, so a pure casing change goes through a temporary intermediate name first. Deliberately diverges from `rename_chapter()`'s behavior on a name collision: `rename_chapter()` silently overwrites an existing target (after a frontend `confirm()`), but `rename_project()` raises `EngineError(409, ...)` instead — overwriting a whole other project's directory as a side effect of a rename was judged too large a blast radius to allow, even with confirmation. No chapter-order or cross-file reference updates are needed (unlike chapter rename touching `_chapter_order.json`), since nothing on disk stores a project's own name inside its contents — a project is purely the directory name itself.

**ZIP entry filenames (2026-08-08; reordered 2026-08-10):** `build_combined_audio_zip(project)` names each entry `<chapter>_<project>_<date>.wav` (`date = datetime.now(UTC).strftime("%Y-%m-%d")`), not just `<chapter>.wav` — matches the same descriptive-filename convention the frontend uses for individual box/chapter downloads (`buildBoxDownloadFilename()`, see `docs/frontend-specification.md` section 3, "Download filename"). The outer `.zip` filename itself is set client-side (`<project>.zip`) and is unrelated to the per-entry names inside it. Initially missed when the box/chapter download renaming first shipped — caught in review, since the ZIP is a separate code path (`GET /projects/{project}/download-all`) from the individual download links. Order changed from `<project>_<chapter>_<date>` to `<chapter>_<project>_<date>` per Danny's `docs/ideas.md:35` note ("erst Kapitel, dann Titel, dann Uhrzeit") — chapter name first makes more sense when browsing a folder of extracted files across projects.

**Variant locking (2026-08-08):** `boxes[i].variantLocks` and the chapter-level `combinedVariantLocks` are sparse `{filename: true}` dicts (only locked filenames present) that mark a variant as protected against deletion. Enforcement lives in `dialog/variants.py`, not just the frontend: `delete_box_variant()`/`delete_combined_variant()` check the relevant lock dict *before* touching the file and raise `EngineError(400, ...)` if the target filename is locked, so a direct API call can't bypass a disabled "✕" button in the UI. `delete_inactive_variants()` (the "Bereinigen"/cleanup endpoint, which otherwise prunes every box/combined variant list down to just its active entry) keeps any locked filename too — `kept = {active_file} ∪ {f for f in variants if locks.get(f)}` per box/chapter, with `activeIndex` re-resolved against the shorter kept list. The pre-existing "no combined variant active → leave the whole list untouched" special case (comparison candidates before any pick was ever made) is unaffected by locks; it only comes into play once something is active. Box-variant locks are threaded through the same untyped draft/chapter-save path as `variantLabels` (see `docs/frontend-specification.md` 1.2) — no dedicated write endpoint. Combined-variant locks *do* get one, `PUT .../combined-variants/{filename}/lock` (`set_combined_variant_lock()`), since combined variants aren't part of the box draft payload and are written by the backend directly (`add_combined_variant()`).

**Clearing a chapter's audio (2026-08-11):** `clear_chapter_audio(project, chapter)` (`dialog/projects.py`) backs the frontend's "Dialog leeren" action (`clear-dialog-btn`) — Danny noticed combined *and* box audio kept reappearing after clicking it ("bei clear bleibt immer noch die combined audio stehen"), because the handler only ever reset browser-side state (`clearBoxesOnly()`, `resetCombinedOutput()`) and wrote to `localStorage`, never touching the server. Like `delete_chapter()`, it 404s if the chapter doesn't exist, then `shutil.rmtree`s the entire `{chapter}_audio` directory in one shot (box takes, box variants, `combined.wav`, combined variants together) rather than deleting each category individually. Unlike `delete_chapter()`, the chapter's own `.json` file and box text survive — only the variant bookkeeping resets: each box's `variants`/`activeIndex`/`variantLocks`, plus the chapter-level `combinedVariants`/`activeCombinedIndex`/`combinedVariantLocks`/`combinedVariantLabels`. New route: `POST /projects/{project}/chapters/{chapter}/clear-audio`. The frontend handler calls this before its existing local reset, then persists the now-blank single-box state via `saveCurrentChapter({ silent: true })` — without that save, the box *text* (untouched by the backend clear on purpose) would still reappear from the old `chapter.json` on the next chapter load, even though the audio wouldn't.

Noted but out of scope for this fix: `save_chapter()` (the regular "Kapitel speichern" route) rebuilds `chapter.json`'s content from just 4 fields (`boxes`, `pause_ms`, `end_pause_ms`, `updated_at`) with no read-modify-write against the existing file, so `combinedVariants`/`activeCombinedIndex`/`combinedVariantLocks`/`combinedVariantLabels` are dropped from the JSON on every normal manual save (the underlying variant files on disk are unaffected, only the list shown in the UI on next load would appear empty).

**Combined-variant labels (2026-08-11):** `combinedVariantLabels`, a chapter-level sparse `{filename: label}` dict, brings the combined-variants list to UI parity with box variants — Danny flagged the combined-variants section as visibly inconsistent with the box-variant rows (`docs/ideas.md`: "design bei combined bei variants hässliche button anordnung, präfixe fehlen, delete all section. sieht nicht aus wie die variants in den boxen"). `set_combined_variant_label()` (`dialog/variants.py`) follows the exact same shape as `set_combined_variant_lock()`: a new `PUT .../combined-variants/{filename}/label` endpoint (`SetVariantLabelRequest`, `schemas.py`), writes immediately to the chapter JSON, no chapter save needed. `delete_combined_variant()` now also pops any label for the deleted filename, same as it already did for locks. Frontend: `renderCombinedVariantsList()` (`dialog-combined.js`) was rebuilt to reuse the exact same `.dialog-box-variant-controls` row layout, `deriveVariantLabel()`/`variantSuffixFromFilename()` (now exported from `dialog-boxes.js` instead of duplicated), rename-pencil flow, and multi-select-checkbox + bulk-delete bar (`.dialog-box-variants-bulk-bar`) that box variants already had — previously it appended activate/lock/delete buttons directly to the row with no wrapper, so they stacked one per line instead of wrapping, and had no label or bulk-delete at all. Selection state for the bulk bar lives in a module-level `Set` (`selectedCombinedVariants`), since combined variants aren't scoped to a single box the way `boxAudioBlobs`' per-box `selectedVariants` is. See `docs/frontend-specification.md` sections 1.2 and 3 ("Box variant system") for the full before/after.

**Skills-Files persistence & routes (2026-08-09, Plan 095; narrowed to skills-only by Plan 108, 2026-08-10):** `dialog/skills_files.py` gives human users view/edit/delete access to the same `data/skills/` directory the chat agents' `SkillsMiddleware` already reads (`SKILLS_DIR`, see Section 3's security note; moved from `src/orchestrator/skills/` on 2026-08-11, see Section 6 — skills are user-editable content, not code). `_resolve_file_path(file_path)` resolves the requested path against `SKILLS_DIR` and checks `is_relative_to()` (the same traversal-safety property `dialog/projects.py`'s `_project_dir()` provides, though `sanitize_name()` itself can't be reused as-is here since these paths may contain a `/`, e.g. `human-style-check/SKILL.md`), then restricts access to a `<skill>/SKILL.md` shape only — a nested non-`SKILL.md` file (e.g. `<skill>/notes.md`) is rejected. Before Plan 108, this module also served any top-level `.md` file directly under `SKILLS_DIR` (`AGENTS.md`, custom memory files) — that whole concern moved to `dialog/project_notes.py` (see "Custom memory files" below), since `AGENTS.md` and its siblings are project-scoped now, not global. `save_file_content()` (the `PUT` route) 404s if the target path doesn't already exist — edit and create are deliberately separate operations, not because creation is disallowed outright.

**Skill creation (2026-08-09):** `create_skill(name, description)` is the dedicated create path, added after Plan 095 initially shipped view/edit/delete only and that turned out to be the wrong scope — the two workarounds documented at the time (ask a chat agent to `write_file` one, or hand-create the file on disk) weren't a real answer for a human user working in the UI. `_sanitize_skill_name()` lowercases the input, turns spaces into hyphens, and strips anything outside `a-z0-9-` (own regex, not `dialog/projects.py`'s `sanitize_name()` — that one permits spaces/dots/underscores, which don't match the existing skill folders' plain-kebab-case convention: `human-style-check`, `story-plot-ideas`, `tag-suggestions`). Raises `EngineError(400, ...)` on an empty/all-invalid-character name, `EngineError(409, ...)` if `<slug>/SKILL.md` already exists (checked before creating the directory, so a collision never partially creates anything). Writes the same frontmatter shape as the three hand-authored skills: `---\nname: <slug>\ndescription: <description>\n---\n\n# <slug>\n\n`, leaving the instructional body empty for the user to fill in via the normal edit/save flow immediately afterward.

**Custom memory files (2026-08-09; rescoped to per-project by Plan 108, 2026-08-10):** `create_memory_file(project, name)` (`dialog/project_notes.py`, `POST /projects/{project}/notes` — moved off `POST /skills-files/memory`, which no longer exists) lets a user create an arbitrary `<name>.md` inside that project's own directory (`data/dialog_projects/<project>/`), e.g. `Charaktere.md` or `Worldbuilding.md` alongside the auto-created `AGENTS.md`. `_sanitize_memory_filename()` (now in `project_notes.py`) still uses `dialog/projects.py`-style sanitization (`\w\- .`, preserving case and spaces) rather than the skill slugifier — these filenames are meant to stay human-readable (`Charaktere.md`, not `charaktere.md`). Appends `.md` if the user didn't type it; 409s on a name collision; writes an empty file — no frontmatter, no starter template (only the auto-bootstrapped `AGENTS.md` gets `DEFAULT_AGENTS_MD`, see "Shared Agent Memory" below). **No `MemoryMiddleware` wiring change was needed for this feature** — `FilesystemMiddleware` already grants a `read_file` tool over the whole per-project directory (see below), so a new note becomes usable the moment `AGENTS.md` (or the agent itself, via its own `write_file`/`edit_file` access) mentions it's worth reading; there is no automatic registration into `MemoryMiddleware(sources=[...])`, which stays hardcoded to `["/AGENTS.md"]` in both `chat_agent.py` and `script_chat_agent.py`. Global skill files have no equivalent "custom file" concept — `dialog/skills_files.py` only ever manages `<skill>/SKILL.md` files (see above).

Deleting a project's `AGENTS.md` is deliberately allowed, not specially blocked — verified safe by reading the actual `deepagents` library source (not assumed) across all three layers a missing file could surface: `MemoryMiddleware.before_agent()` (`deepagents/middleware/memory.py`) treats a `file_not_found` backend response as "no memory loaded" rather than raising; the `edit_file` tool (`deepagents/middleware/filesystem.py`) returns a normal `ToolMessage(status="error")` when the backend reports an error, not an uncaught exception; and `FilesystemBackend.edit()` (`deepagents/backends/filesystem.py`) explicitly checks `resolved_path.exists()` before attempting to read. None of these paths are hit at server startup either — `AGENTS.md` is only read lazily, the first time an actual chat request runs `before_agent()`, not at module import time. If a chat agent's `edit_file` call fails because the file is gone, the model sees a normal tool error and can fall back to `write_file` (which does create the file) — the system prompt already tells it "Use write_file or edit_file" for exactly this reason. Kept deletable after discussing the trade-off (data loss vs. crash risk) explicitly — losing accumulated memory is a real but non-crashing, user-triggered consequence, not a latent bug. Since Plan 108, `_build_agent()` also calls `ensure_agents_md(project_dir)` before constructing the backend on every chat request — so a deleted `AGENTS.md` is silently recreated with `DEFAULT_AGENTS_MD` the next time either chat agent runs for that project, not left missing indefinitely.

Voice reference data lives separately, under `data/audio_data/voices/`: one `.wav` (reference audio) + `.txt` (transcript) pair per voice name, read directly by `engine_client.py` (`list_voices()`, `_load_voice()`). Since 2026-08-12, this is scanned recursively (`rglob`), so voices in subfolders (e.g. `legacy_voices/`) are found too — `_find_voice_dir()`/`_voice_dir()` resolve a voice name to its actual containing folder for every read/write/delete/rename operation.

## 3. Engine Integration

`engine_client.py` talks to the `s2.cpp` TTS engine over HTTP (native server, see `docs/ideas.md`'s "Ziel: Lab für Hörbücher und Dialoge" section for why — a thin orchestrator in front of the native server rather than a `ctypes` wrap, to stay independent of `s2.cpp` updates). Key functions:

- `list_voices()` — voice names available for cloning, derived from `data/audio_data/voices/**/*.txt` (recursive, any subfolder).
- `list_voices_detail()` — returns every voice's `{name, locked, folder, active}` (2026-08-12 adds `folder`/`active` to the pre-existing `locked`, Plan 106). `folder` (`_voice_folder()`) is the voice's immediate subfolder name relative to `VOICES_DIR`, or `None` for voices directly in `VOICES_DIR` **and** for anything under `legacy_voices/` (deliberately excluded from the folder-grouping UI — see `frontend-specification.md`). `active` reflects `is_voice_active()` (see below). Always returns *all* voices regardless of `active` state — this is the one place an inactive voice must still be visible, since it's how you reactivate it.
- `is_voice_active(name)` / `set_voice_active(name, active)` (2026-08-12) — an `<name>.hidden` marker file (analogous to `.lock`), default active (no marker = active, so existing voices are unaffected until explicitly toggled). `set_voice_active` touches/removes the marker.
- `list_active_voices()` (2026-08-12) — `list_voices()` filtered to `is_voice_active()`. Used by `GET /voices` (the box voice `<select>` dropdown) and the script-chat's voice-context message (`routers/chat.py`'s `_voices_context_message()`) — inactive voices disappear from both places at once. Internal validation (`_require_known_voice`, name-collision checks in `create_voice`/`rename_voice`) deliberately keeps using the unfiltered `list_voices()`, so an inactive voice still blocks a name collision and generation with an inactive voice (e.g. from an existing box) still works.
- `create_voice(name, audio_bytes, text)` — writes a new reference `.wav` and `.txt` pair to `data/audio_data/voices/` (Plan 105). Uses a local import of `sanitize_name` from `dialog/projects.py` to prevent circular imports at module load time, validates audio format via `_read_wav_as_pcm16()`, and raises `EngineError(409)` on name collision.
- `set_voice_locked(name, locked)` — creates or removes `<name>.lock` marker file (Plan 106).
- `delete_voice(name)` — unlinks `.wav`, `.txt`, `.lock`, and `.hidden` for a voice; raises `EngineError(400)` if locked (Plan 106).
- `rename_voice(old_name, new_name)` — renames `.wav` and `.txt` files (and `.hidden` if present, since 2026-08-12); raises `EngineError(400)` if locked and `EngineError(409)` on collision (Plan 106).
- `generate_speech(text, voice)` — the core TTS call; `voice=None` uses `base_voice` (free generation, no reference audio). Blocking/synchronous, called from a synchronous (`def`, not `async def`) route handler (`routers/variants.py`'s `project_box_generate_variant`), so FastAPI runs it in a worker thread with no `request.is_disconnected()` check anywhere in the call chain — a client that aborts its fetch (e.g. the "Cancel" button, or navigating to a different chapter) does not stop this call; the engine keeps rendering the full clip and `add_box_variant()` still writes it to disk regardless. There is no real cancellation path server-side, only client-side bookkeeping of what to do with an already-finished result — see `docs/frontend-specification.md` (section 4.3) and `docs/FIXES.md` (2026-08-17) for how the frontend works around this instead of pretending to cancel it.
- `get_voice_preview(voice)` — returns the raw reference `.wav` for frontend preview playback.
- `engine_ready()` (2026-08-11) — cheap liveness check for `GET /engine/status`, used by the frontend's engine-loading overlay (see `frontend-specification.md`). Any HTTP response counts as ready (even a 404 — it just means the engine process is up and listening), only a connection failure means not ready.

Errors from the engine surface as `EngineError(status_code, detail)`, caught at the router layer and converted to the matching `HTTPException`.

### Chat Agents & LLM Provider Factory (Plan 093)

Both LangChain agents (`langchain.agents.create_agent`) back their respective SSE-streaming endpoints in `routers/chat.py`. Instead of a static module-level singleton, agents are constructed per request via `_build_agent(provider, model)`, calling the shared factory `build_chat_model()` in `agents/llm_provider.py`.

- **`provider == "ollama"`**: Returns a `ChatOllama` instance configured with `reasoning=True` and the requested model, falling back to `OLLAMA_MODEL` from `.env` if the request didn't specify one. No hardcoded default model name (changed 2026-08-10, `docs/FIXES.md`) — a fixed string only ever matches whichever machine set it, not a fresh clone's actual installed models. Raises `ValueError` if neither an explicit model nor `OLLAMA_MODEL` is available (router translates this into HTTP `400`).
- **`provider == "nvidia"`**: Checks for `NVIDIA_API_KEY` in environment variables and returns a `ChatNVIDIA` instance for the specified model ID. Raises `ValueError` if the key is missing or no model is specified (router translates this into HTTP `400`).
- **NVIDIA Model Probe Route**: `GET /api/llm/nvidia-models` is a plain `def` (not `async def`) route — it calls `fetch_verified_nvidia_models()` (`utils/verify_nvidia_models.py`), which does many parallel live HTTP probes and can take a while; FastAPI runs sync `def` routes in a worker thread automatically, so this doesn't block the event loop the way an `async def` calling it directly would. Returns `{"models": []}` (HTTP `200`, not an error) if `NVIDIA_API_KEY` is not set on the server. **Cached for the server's lifetime**: a module-level `_nvidia_models_cache` in `routers/chat.py` holds the first successful result; every later call returns it immediately without re-probing, until the server process restarts. The "no key" empty result is deliberately *not* cached (cheap to recompute, and setting the key still requires a restart anyway since `.env` is only read once at import time).
- **Ollama Model List Route**: `GET /api/llm/ollama-models` calls `fetch_ollama_models()` (`utils/fetch_ollama_models.py`) — a single, fast local call to Ollama's own `GET /api/tags`, filtered to models whose `capabilities` list includes `"completion"` (excludes embedding-only models like `nomic-embed-text`). No live probing, no caching — cheap enough to call on every page load. Returns `[]` if Ollama isn't reachable (`httpx.ConnectError`/`TimeoutException`/`HTTPStatusError` all caught). Also returns `default_model` (`os.getenv("OLLAMA_MODEL")`, `null` if unset), added 2026-08-10 so the frontend can offer it as a labeled fallback option (`"<model> (.env)"`) when no local models are found, instead of wrongly claiming chat is unavailable when the `.env` fallback would actually still work — see `docs/frontend-specification.md` item 15.

### `agents/chat_agent.py` — per-box chat

`POST /projects/{project}/chapters/{chapter}/boxes/{box_index}/chat`. Rewrites the text of a single dialog box. Middleware: `FilesystemMiddleware(tools=["ls", "read_file", "write_file", "edit_file", "glob", "grep"])` + `SkillsMiddleware(sources=["/skills/"])` + `MemoryMiddleware` (Plan 087; `SkillsMiddleware` added alongside the box chat's memory support on 2026-08-07, same skills as the script chat below) — since Plan 108, `FilesystemMiddleware`/`MemoryMiddleware` bind to a per-project `FilesystemBackend`. Since 2026-08-11, `FilesystemMiddleware` and `SkillsMiddleware` both bind to a `CompositeBackend` (project directory as `default`, `SKILLS_DIR` routed at `/skills/`) instead of `FilesystemMiddleware` being bound to the skills directory alone — see "Shared Agent Memory" below for why and the bug this fixed. Since 2026-08-10, `MemoryMiddleware` uses a project-specific `system_prompt=PROJECT_MEMORY_SYSTEM_PROMPT` (`agents/memory_prompt.py`) instead of deepagents' library default — see "Shared Agent Memory" below.

### `agents/script_chat_agent.py` — whole-script chat

`POST /projects/{project}/chapters/{chapter}/script-chat`. Rewrites the entire multi-speaker script text at once (`Sprecher: Text` per line). Accepts `allow_extend_recorded_roles: bool = False` in `ChatRequest` (Plan 107), dynamically appending instructions to `_build_system_prompt(allow_extend_recorded_roles)` via `_build_agent(provider, model, project, allow_extend_recorded_roles)` (Plan 108 inserted `project` as a new parameter). Middleware: `FilesystemMiddleware(tools=["ls", "read_file", "write_file", "edit_file", "glob", "grep"])` + `SkillsMiddleware(sources=["/skills/"])` + `MemoryMiddleware`. Since 2026-08-11, both `FilesystemMiddleware` and `SkillsMiddleware` bind to the same `CompositeBackend` described in "Shared Agent Memory" below, instead of Plan 108's two separate `FilesystemBackend` instances (one per-project, one global for `SkillsMiddleware`). `SkillsMiddleware` discovers every `*/SKILL.md` under `src/orchestrator/skills/` live from disk on each request; currently `tag-suggestions`, `human-style-check`, `story-plot-ideas`, `worldbuilding-skill`, and `character-writing`.

**Completeness contract, fixed 2026-08-09:** `system_prompt` now explicitly requires the model to reply with the *complete* script text (all existing lines plus any edit/addition) whenever the request is a text change or continuation — with an explicit example for "führe den Dialog fort"-style continuation requests, since that phrasing especially invited the model to reply with only the new lines instead of restating everything. A separate carve-out lets the model answer freely, without repeating the script, for pure questions that don't request a text change (e.g. "was fällt dir an Sprecher X auf?"). Before this fix the prompt had no completeness rule at all — unlike `agents/chat_agent.py`'s box-chat prompt, which has always had the equivalent "reply with nothing but the revised box text" contract (Plan 087-era) — even though the frontend's `onApply` (`dialog-script-mode.js`) has always done a full-textarea replace, not an insert. The mismatch between an always-full-replace UI and a prompt with no completeness guarantee was the actual bug Danny reported.

**No-Markdown rule, added 2026-08-09:** Both `chat_agent.py` and `script_chat_agent.py` now explicitly forbid Markdown formatting in `system_prompt` (no `**bold**`, no `_italic_`, no bullet/numbered lists, no `#` headings) — neither prompt mentioned Markdown before this. For the box chat this is a TTS-quality concern: the reply is read aloud verbatim, and stray `**`/`#` characters would be spoken literally. For the script chat it is also a parser-correctness bug, not just style: `parseScriptTurns()` (`static/js/dialog-script-mode.js:69-85`) matches the leading `Sprecher:` token via an exact, case-insensitive string match against the real voice list. A markdown-bolded name like `**Anna:** Hallo` is captured as speaker `**Anna**`, which never matches voice `Anna` — the line silently gets appended to the previous turn's text instead of starting a new box. The script-chat prompt's no-markdown sentence names this failure mode explicitly so the model understands *why*, not just that the rule exists.

**Third reason for the no-`**bold**` rule, per Danny (2026-08-11):** `s2-pro` itself sometimes interprets `**bold**` markup in a speaker's spoken text as a shouting cue — an emergent model behavior, not something this codebase implements or controls. This project already has a dedicated, deliberate way to request shouted delivery (the fixed `[shouting]` tag, `tags.py`), so `**bold**` slipping into generated box/script text would be an unintended, uncontrolled trigger for the same effect. Reinforces rather than changes the existing rule above — no code change, this is additional justification for a rule that already existed. **No-emoji rule added the same day** (`docs/ideas.md`, `chat_agent.py`/`script_chat_agent.py`/`project_chat_agent.py`/`memory_prompt.py` system prompts): same TTS-unspeakable-character reasoning as the markdown rule for the two box/script-facing agents; for `project_chat_agent.py` the rule is scoped to its `.md` file writes specifically (normal Markdown structure — headings, lists, bold — stays allowed there, since notes files are never spoken by TTS, only emojis are banned).

### Shared Agent Memory (`AGENTS.md`), Plan 087, Plan 092 & Plan 108

Each dialog project has its own persistent memory file (`AGENTS.md` located directly inside `data/dialog_projects/<project_name>/AGENTS.md`), initialized from a default template (`DEFAULT_AGENTS_MD` in `dialog/projects.py` with `# Agent Memory`, `## Charaktere`, and `## Worldbuilding` headings) whenever a new project is created/saved.

Both chat agents (`chat_agent.py` and `script_chat_agent.py`) construct a dedicated `FilesystemBackend` for the target project (`project_backend = FilesystemBackend(root_dir=_project_dir(project), virtual_mode=True)`), passed to `MemoryMiddleware(backend=project_backend, sources=["/AGENTS.md"])`.

**`CompositeBackend` for `FilesystemMiddleware`/`SkillsMiddleware` (fixed 2026-08-11, see `docs/FIXES.md`):** both agents also build `project_and_skills_backend = CompositeBackend(default=project_backend, routes={"/skills/": skills_backend})` (`deepagents.backends`) and pass it to both `FilesystemMiddleware` and `SkillsMiddleware(sources=["/skills/"])`. Before this fix, `FilesystemMiddleware` (the middleware that actually grants `ls`/`read_file`/`write_file`/`edit_file`/`glob`/`grep` tools) was bound to `skills_backend` alone — box chat and script chat could browse and edit `src/orchestrator/skills/`, but had no tool-based access to the project directory at all; `MemoryMiddleware`'s auto-injected `AGENTS.md` content was the *only* project data either agent ever saw, and there was no way to search for or read any other project file. `CompositeBackend` routes any path starting with `/skills/` to `skills_backend` and everything else (including `/AGENTS.md` and any other project file) to `project_backend`, so a single `FilesystemMiddleware` instance now reaches both. `SkillsMiddleware` must use the *same* composite backend and `sources=["/skills/"]` (not the bare `skills_backend`/`sources=["/"]` it used before) — it reports each skill's `SKILL.md` path in the system prompt ("read `{path}` for full instructions"), and that path must be resolvable by `FilesystemMiddleware`'s `read_file` tool; with the old `sources=["/"]`, the reported path (e.g. `/tag-suggestions/SKILL.md`) had no `/skills/` prefix and would have 404'd against the new composite-backed `read_file` tool. `project_chat_agent.py` (below) had this exact `SkillsMiddleware` path mismatch independently since Plan 109 — its `FilesystemMiddleware` never reached `SKILLS_DIR` at all, composite or not, until this same fix.

Since 2026-08-10, both `MemoryMiddleware(system_prompt=...)` calls pass `PROJECT_MEMORY_SYSTEM_PROMPT` (`agents/memory_prompt.py`) instead of leaving the argument unset (deepagents' own `MEMORY_SYSTEM_PROMPT` default, generic Slack/calendar examples not relevant to this project). The custom prompt spells out concrete write-worthy/not-write-worthy examples for a TTS dialog project, and states explicitly that "noting something" always means an actual `edit_file`/`write_file` tool call, never just a sentence in the reply — the deepagents default only implied this. `project_chat_agent.py` (below) uses a second, near-identical constant, `PROJECT_CHAT_MEMORY_SYSTEM_PROMPT`, whose only difference is that it explicitly permits creating new topic-named files on its own initiative, matching that agent's broader mandate.

All project-scoped `.md` notes (including `AGENTS.md` and custom notes like `Charaktere.md`) are managed via `src/orchestrator/dialog/project_notes.py` and exposed via REST routes under `/projects/{project}/notes` (`src/orchestrator/routers/project_notes.py`). Global skills remain under `/skills-files` (`dialog/skills_files.py`), with top-level memory file creation removed from `skills_files.py`. The old single global `src/orchestrator/skills/AGENTS.md` was removed.


### Project Chat Agent (`project_chat_agent.py`), Plan 109

A third, project-scoped chat agent (`src/orchestrator/agents/project_chat_agent.py`) handles onboarding conversations for new projects. It binds `FilesystemMiddleware` with full `["ls", "read_file", "write_file", "edit_file", "glob", "grep"]` permissions to the same `CompositeBackend` shape described above (project directory as `default`, `SKILLS_DIR` routed at `/skills/`) — as of 2026-08-11 this is no longer a distinguishing feature versus `chat_agent.py`/`script_chat_agent.py` (all three now share it), but it's what lets the onboarding agent autonomously create and update any `.md` file in the project directory (e.g., `AGENTS.md`, `Charaktere.md`, `Welt.md`) without requesting explicit user permission. Before the 2026-08-11 fix, this agent's `FilesystemMiddleware` was bound to `project_backend` alone, and its `SkillsMiddleware` reported unreachable skill paths (see above) — it had no working access to `src/orchestrator/skills/` at all, composite backend or not. Exposed via `POST /projects/{project}/chat` in `src/orchestrator/routers/chat.py` using `ProjectChatRequest`.

Since 2026-08-10, it *also* carries a `MemoryMiddleware(backend=project_backend, sources=["/AGENTS.md"], system_prompt=PROJECT_CHAT_MEMORY_SYSTEM_PROMPT)`, on top of the `FilesystemMiddleware` above. `FilesystemMiddleware` alone only lets the model read `AGENTS.md` if it decides to call `read_file` — model compliance isn't guaranteed, especially on smaller local models. `MemoryMiddleware`'s `before_agent` hook loads `AGENTS.md` unconditionally on every turn and injects it into the system prompt, so existing project notes are always in context even if the model never explicitly reads the file.



### Reasoning Stream & SSE Event Format (Plan 088)

Both chat agents configure `ChatOllama(model=OLLAMA_MODEL, reasoning=True)` and yield `(chunk_type, text)` tuples (`"reasoning"` or `"content"`) from `stream_chat_reply()` / `stream_script_chat_reply()`. `routers/chat.py` uses a shared `_format_sse_chunk(chunk_type, text)` helper: `"content"` chunks yield standard `data: {"chunk": "..."}\n\n` frames, while `"reasoning"` chunks yield `event: reasoning\ndata: {"chunk": "..."}\n\n` frames.

## 5. Audio DSP Pipeline

`src/orchestrator/audio/` — pure functions operating on PCM16 bytes, no FastAPI dependency, each independently testable:

- `combine.py` — `concat_wavs()`: joins multiple clips with configurable pauses/gains/pans between them.
- `trim.py` / `fade.py` — clip trimming and fade-in/out.
- `compressor.py` — dynamics compressor (threshold/ratio/attack/release), vectorized (Plan 084).
- `reverb.py` — Dattorro plate reverb, numba-JIT-compiled tank (Plan 081).
- `eq.py` — graphic EQ (peaking-filter bands), `scipy.signal.lfilter`-vectorized (Plan 079), framerate-aware band validation (`_validate_framerate()`).
- `normalize.py` — Peak/RMS/LUFS normalization; LUFS mode is the project's first external DSP dependency (`pyloudnorm`), Peak/RMS stay standard-library.
- `pitch.py` / `formant.py` — pitch/formant shifting (semitones + cents), `librosa`-based.
- `delay.py` — tape-style feedback delay (delay_time_ms, feedback, damping, saturation, wow/flutter rate/depth, wet/dry mix), numba-JIT-compiled channel processing (Plan 096). Unlike Reverb, preserves input channel count (mono stays mono, stereo stays stereo). `_estimate_tail_seconds` appends a 60dB decay tail (capped at 20 seconds).
- `mp3.py` (added 2026-08-10) — `wav_to_mp3(wav_bytes, bit_rate_kbps=320)`, second external dependency after `pyloudnorm` (`lameenc`, a pure-pip wrapper around LAME, no system `ffmpeg` binary needed). Only used by `dialog/projects.py`'s `build_combined_audio_zip(project, audio_format="wav"|"mp3")`, itself only reachable via `GET /projects/{project}/download-all?audio_format=mp3`. Note: MPEG Layer III caps CBR at 160 kbps below 32 kHz sample rate (MPEG-2) — 320 kbps only holds at the project's actual 44100 Hz output (see `docs/ideas.md`'s framerate correction).

All effects share the table-driven route registration in `routers/effects.py` (`EffectSpec`, Plan 085) and per-box/combined parameter persistence via `dialog/effect_params.py`.

## 6. Desktop Packaging (Tauri Prototype, 2026-08-11)

A Tauri desktop shell (`src-tauri/`) wraps the existing web app in a native window, spawning the orchestrator and the `s2.cpp` engine itself instead of requiring `start.bat`. Entirely additive — `start.bat`/browser usage is unaffected.

**`paths.py`** is the load-bearing piece that makes this possible: it distinguishes `RESOURCE_DIR` (bundled read-only assets — `static/`; resolves to PyInstaller's `sys._MEIPASS` when frozen) from `EXE_DIR`/`DATA_DIR` (writable, next to the executable — voices, dialog projects, skills). In normal (`uv run`) execution both resolve to the repo root, unchanged from before this module existed. Detection is `getattr(sys, "frozen", False)`.

**`run_desktop.py`** (repo root) is the PyInstaller entry point — a plain `uvicorn.run(app, host="127.0.0.1", port=8000)` call, since PyInstaller needs a script, not a CLI invocation like `uvicorn src.orchestrator.main:app`.

**Packaging shape matters:** the orchestrator is built with PyInstaller `--onedir` (not `--onefile`) and bundled as a Tauri resource, spawned via a plain `Command` — not Tauri's `externalBin`/"sidecar" mechanism. Reason: PyInstaller onefile builds spawn an internal second process on Windows (bootloader hands off to a real worker process), and that worker survives if only the bootloader's PID is killed — found via a real orphaned-process bug in testing, fixed by switching to onedir (no such split) for both the orchestrator and the engine. `s2.exe` was already resource-bundled rather than sidecar'd regardless, since it needs its DLLs and the ~5.6 GB model file (`s2-pro-q8_0.gguf`) in the same directory, not a single standalone binary.

Both processes are spawned in `src-tauri/src/lib.rs`'s `setup()` hook and killed via `taskkill /PID <pid> /T /F` (not just `CommandChild::kill()`) on `RunEvent::ExitRequested` — the `/T` (tree) flag matters even with onedir, since child processes were still observed under both `orchestrator.exe` and `s2.exe` at kill time.

`GET /engine/status` (`engine_client.engine_ready()`) exists specifically to back a loading overlay (`static/js/engine-loading.js`) — the engine takes ~10-45s to load the model onto the GPU, during which the orchestrator itself is already up and serving pages.

**`static/loading.html`** covers the gap *before* that: the window's initial `url` is this local, Tauri-bundled page (not the orchestrator's `/app`), so something renders immediately even before the orchestrator itself has finished starting. `static/js/startup-redirect.js` polls the same `/engine/status` endpoint (tolerating connection failures while the orchestrator isn't up yet) and `window.location.replace()`s to `/app` once it responds — from there the in-page overlay above takes over. Required removing `build.devUrl` from `tauri.conf.json`: a relative window `url` resolves against `devUrl` rather than `frontendDist` whenever it's set, even outside the `tauri dev` CLI workflow, which broke this against the orchestrator's own origin (404) — see `docs/infos.md` and `docs/FIXES.md` (2026-08-11).
